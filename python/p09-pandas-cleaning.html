9. pandas: cleaning, grouping, joining

Python · Unit 9

P9 · Python Reading: 8 pages With practice: ≈ 2 hours Assumes: P8

Why this unit is here

Three operations account for most of the work in most analyses: deciding what to do about missing values, summarising by group, and combining two tables.

None of them is technically hard. All three are easy to get quietly wrong — a dropna() that removes a fifth of your data, a join that duplicates rows, a group mean computed over a different set of rows than you thought. This unit is about making each of those decisions visible.

Before you start

You should be able to:

  • load a table, check its dtypes, and select rows by condition — P8;
  • explain why .copy() matters after a row selection — P8;
  • write an assertion — P5.

Quick check. After subset = frame[frame["x"] > 0], why might writing to subset not affect frame?

TipShow the answer

Because the selection produced a separate object. pandas does not promise whether it is a view or a copy, which is why you add .copy() when you intend an independent table and use frame.loc[mask, col] = ... when you intend to write into the original.

The idea

import pandas as pd
from pathlib import Path

cohort = pd.read_csv("../data/cohort.csv")
for column in ("diagnostic_score", "hours_practice", "final_score"):
    cohort[column] = pd.to_numeric(cohort[column], errors="raise")

print(cohort.shape)
print(cohort.isna().sum())
(240, 7)
student_id          0
background          1
diagnostic_score    0
hours_practice      0
final_score         1
completed           0
started_on          0
dtype: int64

Two missing values, in different columns and different rows. Before touching them, ask the question this unit turns on: why is it missing?

  • The score was never recorded because the student withdrew — the missingness is related to the outcome, and dropping the row biases the result.
  • The score was lost in a transcription error — unrelated to the outcome, and dropping is comparatively harmless.
  • The field does not apply to that student at all — structurally missing, and the row may belong to a different population.

pandas cannot tell you which. dropna() will happily proceed under all three, which is why it is a decision, not a cleaning step.

The mechanics

Look at missingness before removing it

missing_by_group = (
    cohort.assign(no_score=cohort["final_score"].isna())
    .groupby("background", dropna=False)["no_score"]
    .agg(["sum", "size", "mean"])
    .rename(columns={"sum": "missing", "size": "n", "mean": "proportion"})
)

One missing value, in one group. If instead it had been forty, all in the lowest scoring group, complete-case analysis would systematically overstate the cohort mean — and the number would look perfectly reasonable.

Note dropna=False in the groupby: without it, the row whose background is missing would vanish from this very summary, which is the opposite of what a missingness report is for.

Split, and keep both halves

valid = (
    cohort["final_score"].between(0, 100)
    & cohort["final_score"].notna()
    & cohort["background"].notna()
)

analysis = cohort.loc[valid].copy()
excluded = cohort.loc[~valid].copy()
excluded["reason"] = [
    "final_score missing" if pd.isna(r.final_score)
    else "background missing" if pd.isna(r.background)

Grouping: split, apply, combine

summary = (
    analysis.groupby("background", as_index=False)
    .agg(n=("final_score", "size"),
         mean_score=("final_score", "mean"),
         sd_score=("final_score", "std"),
         mean_hours=("hours_practice", "mean"))
    .round(2)
)
summary
background n mean_score sd_score mean_hours
0 Computing 69 65.85 6.60 12.47
1 Engineering 36 67.15 5.33 10.45
2 Life sciences 57 60.51 7.29 22.61
3 Mathematics or Physics 36 75.28 7.63 8.03
4 Social sciences 39 60.21 6.58 27.37

as_index=False keeps background as an ordinary column rather than moving it into the index, which makes what follows simpler. The named arguments to .agg give each output column an explicit name, so you never have to decode a multi-level heading.

pandas’ .std() uses the \(n-1\) divisor by default — the sample standard deviation, the opposite of NumPy’s default. That inconsistency is real and worth remembering; P7 covers the NumPy side.

Two arguments do the work here, and they should be habits.

validate="one_to_one" states the relationship you believe holds — one summary row per background, one metadata row per background — and pandas raises if it does not. A join that unexpectedly matches many-to-many silently multiplies your rows and changes every downstream number.

indicator=True adds a column saying, for each row, whether it matched on both sides. Checking it catches the other failure: a key that quietly matched nothing and left NaN where you expected data.

Worked example

The whole pipeline, with every decision recorded.

OUT = Path("_outputs")
OUT.mkdir(exist_ok=True)

# 1. load and convert deliberately
raw = pd.read_csv("../data/cohort.csv")
for column in ("diagnostic_score", "hours_practice", "final_score"):
    raw[column] = pd.to_numeric(raw[column], errors="raise")

# 2. split into analysis and exclusions, keeping both
valid = (raw["final_score"].between(0, 100)
         & raw["final_score"].notna()
         & raw["background"].notna())
analysis, excluded = raw.loc[valid].copy(), raw.loc[~valid].copy()

# 3. summarise by group
summary = (analysis.groupby("background", as_index=False)
           .agg(n=("final_score", "size"),
                mean_score=("final_score", "mean"),
                sd_score=("final_score", "std"))
           .round(2))

# 4. join metadata, with the relationship asserted
meta = pd.read_csv("../data/background_meta.csv")
report = summary.merge(meta, on="background", how="left",
                       validate="one_to_one", indicator=True)
assert (report["_merge"] == "both").all(), "a group had no metadata"
report = report.drop(columns="_merge")

# 5. write both results
report.to_csv(OUT / "group_summary.csv", index=False)
excluded.to_csv(OUT / "excluded_rows.csv", index=False)

print(f"{len(analysis)} analysed, {len(excluded)} excluded")
print(f"wrote {OUT/'group_summary.csv'} and {OUT/'excluded_rows.csv'}")

Five steps, and the two that people skip are steps 2 and 4. Keeping the excluded rows means someone can ask which ones? and get an answer. Validating the join means the row count cannot silently change under you.

assert len(analysis) + len(excluded) == len(raw)
assert report["n"].sum() == len(analysis)
print(f"{report['n'].sum()} students across {len(report)} groups "
      f"= {len(analysis)} analysed. Nothing lost, nothing duplicated.")
237 students across 5 groups = 237 analysed. Nothing lost, nothing duplicated.

That last assertion is the one that catches a bad join: if the merge had duplicated rows, the group counts would no longer add up to the number of students.

Try it yourself

Exercise 1 frame.dropna() removes 40% of your rows. Name two things you would check before accepting that, and one before rejecting it.

TipShow the solution

Before accepting:

  • Which columns the missingness is in. dropna() with no arguments drops a row if any column is missing, including ones you never use. subset= limits it to the columns that matter.
  • Whether missingness relates to the outcome. Group the missing indicator by anything you know about the rows, as in the missing_by_group table above. If missing rows differ systematically, complete-case analysis is biased.

Before rejecting: whether the rows are missing structurally — a field that does not apply to that kind of record. Those rows may simply not belong to the population you are describing, and removing them is correct.

Exercise 2 After a merge, your table has 340 rows where both inputs had 240. What happened, and which one argument would have caught it?

TipShow the solution

The key is not unique on the right-hand side, so some left rows matched several right rows and were duplicated.

validate="many_to_one" — or "one_to_one" if you believe both sides are unique — makes pandas raise instead of silently multiplying.

Why it matters beyond tidiness: every duplicated row now contributes more than once to every mean, count and model that follows, and nothing about the output looks wrong.

Exercise 3 Produce a table of the mean diagnostic_score and mean final_score per background, sorted by mean final score descending. Then say what the ordering shows.

TipShow the solution 
(analysis.groupby("background", as_index=False)
 .agg(diagnostic=("diagnostic_score", "mean"),
      final=("final_score", "mean"))
 .round(2)
 .sort_values("final", ascending=False))

The ordering by final score is almost exactly the ordering by diagnostic score — groups that arrived ahead finished ahead. That is the confounding structure planted in this dataset, and it is why the overall relationship between practice and score points the wrong way. S12 takes it apart properly.

Common wrong turns

Where this usually goes wrong

dropna() as a cleaning step
It is a statistical decision about the population you are describing. Look at where the missingness is and whether it relates to the outcome first, and use subset= so unrelated columns cannot remove rows.
Merging without validate
An unexpected many-to-many join multiplies rows and changes every number that follows, with no error. State the relationship and let pandas enforce it.
Not checking indicator
A key that matched nothing leaves NaN rather than an error. The indicator column turns that into something you can assert on.
Assuming .std() matches NumPy
pandas uses the \(n-1\) divisor by default, NumPy uses \(n\). Two “standard deviations” of the same column can differ for this reason alone.
Grouping with dropna=True in a missingness report
The rows whose key is missing disappear from the very summary meant to find them.
Discarding the excluded rows
Then nobody, including you, can answer “which ones, and why?”. Write them out.

TipShow the answers

  1. (b) any column. Which is why a column you never use can silently remove rows. Use subset= to name the columns that matter.

  2. A join whose key is not unique where you assumed it was, which duplicates rows and changes every downstream number without raising.

  3. Because rows whose grouping key is itself missing would be dropped from the report — hiding exactly the cases the report exists to find.

  4. The merge duplicated rows: a key matched more than once on the right-hand side. validate= would have raised instead.

  5. Right: the values are missing structurally — the field does not apply — so those rows are not part of the population being described. Not right: the values are missing because of the outcome, e.g. students who did badly withdrew before the final score was recorded. Then complete-case analysis systematically overstates the result.
